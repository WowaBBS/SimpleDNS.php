# Известные ограничения

Здесь собрано то, что осознанно не сделано или упирается в провайдеров.
Прежде чем «чинить», проверьте живьём: часть пунктов — не баги.

## Транспорты

**QUIC / DoQ.** `DoqTransport` — заглушка. В PHP нет QUIC: ни в потоках, ни в curl
(там только HTTP/3, и то при QUIC-сборке libcurl). Реальный путь — расширение
`php-quic`, собранное на OpenSSL 3.5+, тогда `DoqTransport::supported()` вернёт true
и оживёт уже написанная ветка. Ветка не покрыта тестами: без расширения её не на чем
проверить.

**Quad9 требует HTTP/2.** На POST `https://dns.quad9.net/dns-query` по HTTP/1.1
приходит `505 HTTP Version Not Supported`; через HTTP/2 (curl) тот же запрос
работает. Потоки PHP умеют только HTTP/1.1, поэтому Quad9 недоступен, пока не
появится curl-путь в DoH. Дополнительно: ext-curl в некоторых сборках идёт без
CA-бандла, и тогда нужен `CURLOPT_CAINFO`.

**DoQ/DoH3 через curl.** `curl_version()['features'] & CURL_VERSION_HTTP3` может быть
ложным даже при наличии константы `CURL_HTTP_VERSION_3`. Проверяйте бит, а не факт
наличия константы.

## DoH и JSON

**`?dns=` — не JSON-канал.** У проверенных серверов (Cloudflare, Google) GET с
`?dns=<base64url>` возвращает wire, а не JSON. `DohTransport::JSON_GET` оставлен для
серверов, которые всё же умеют JSON по RFC 8484; на практике используется
`JSON_PARAMS` (`?name=&type=`).

**DNSSEC в JSON — через `do=1`.** Без этого параметра Cloudflare и Google не
присылают RRSIG; dns.sb присылает всегда. `DohTransport` добавляет `do=1`, если
в запросе есть OPT с флагом DO.

**Cloudflare строг к `Accept`.** Отвечает `400` даже на `Accept: */*`; работает
только `application/dns-json` (константа `DohTransport::JSON_ACCEPT`).

**Формат ответа у серверов разный.** Google может отдавать `"type": "a"` строчными
и числа в `TTL`; dns.sb для подписанных зон присылает RRSIG в презентационном виде.
Разбор это уже учитывает (регистр ключей и мнемоник, числовой тип), но новый сервер
может принести очередное расхождение — тогда добавляйте тест с реальным ответом.

## Локальная сеть

**mDNS и LLMNR — только IPv4-группы.** `224.0.0.251` и `224.0.0.252`; IPv6-группы
`ff02::fb` / `ff02::1:3` не реализованы. AAAA-адреса из ответов разбираются, но
запросы по IPv6 не уходят.

**Нет кэша и known-answer suppression.** Каждый вызов — новый запрос и окно
ожидания; ответы от разных хостов объединяются с дедупликацией.

**В группу не вступаем.** mDNS просит юникаст-ответ QU-битом, LLMNR отвечает
юникастом на нестандартный порт источника. Если сеть/файрвол режет входящий UDP
на эфемерный порт, ответы не придут.

**Multicast не выходит за пределы сегмента.** Через роутер, VLAN и изоляцию клиентов
на гостевом Wi-Fi mDNS/LLMNR/NBNS не видны.

## NetBIOS (NBNS)

**Только запросы.** `NbnsClient` умеет NBSTAT и разрешение имени. Регистрация,
release, WACK-челлендж и логика node-type не реализованы.

**Только IPv4** и никакого WINS-специфичного поведения сверх юникаст-запроса.

**Broadcast требует разрешения в файрволе.** Ответ на свой же broadcast Windows
обычно не присылает — это нормально.

## Модель DNS

**A/AAAA не проверяют семейство адреса.** `new ARecord('::1')` даст 16 байт в
A-записи (и наоборот). Проверка длины после `inet_pton` не сделана — известная
дыра, ждёт своего часа.

**Презентационный формат читается регэкспами.** В `MxRecord`, `SoaRecord`,
`SrvRecord`, `CaaRecord`, `TxtRecord` разбор `Data` идёт через `preg_match` /
`preg_split`; единого токенизатора (TextReader) пока нет.

появляются рядом со скриптами и не добавлены в `.gitignore`.

автозагрузки. Не добавляйте PHPUnit без прямой просьбы.
